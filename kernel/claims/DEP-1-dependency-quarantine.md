# DEP-1: Dependencies are quarantined, pinned exactly, and restored in locked mode

**Statement.** Never install a freshly published package. Default cooling-off window: 30 days from publish, and the number lives in exactly one place, the `VERSIONS.md` ledger header, which this claim points at (ruled 30 at extraction; raised to 90 by invariants pass R12, 2026-07-11, on the grounds that 30 contradicted the owner's standing 90-day policy; returned to 30 by owner ruling at the window pass, 2026-07-26, as excessive in practice, the evidence being that 90 produced a dependency with no version satisfying both the window and a live advisory: see the window pass note in the catalog README); hard floor: 7 days for a new package or a new major or minor version, below which no ordinary waiver exists; above the floor, a waiver requires an explicit owner decision conditioned on a recorded supply-chain audit (advisory-database sweep over the exact dependency set). The one carve-out below the floor is a patch release of an already-ledgered dependency, from the same maintainer, that addresses a published advisory: it may bypass the cooling-off window with an explicit owner decision and a ledger row, because remaining on a known-exploited version is the larger risk. The cooling-off reasoning targets new code from new maintainers, not a security patch to a vetted dependency; a floor with no CVE carve-out would, at worst, mandate staying exploited. Where no available version satisfies both the window and a live advisory at once, **the advisory outranks the window, above the hard floor**: a version clearing a published advisory against a ledgered dependency may be taken before it clears the cooling-off window, by explicit owner decision, provided it is at or above the 7-day floor, which never bends. This is the carve-out above reasoned one step out rather than a new policy, and the case is not hypothetical or rare: a window of any length can fail to overlap the set of releases clearing a live advisory, and shortening the window changes the odds without changing the shape. Deciding nothing is not neutral, because a resolver left to itself maximizes version subject to a range and has never heard of either rule, so what it picks is uncorrelated with both and is frequently worse than either rule taken alone. **Any pin taken under this rule carries a ledger row, whether the dependency is direct or transitive**, naming the advisory, the decision, and the date the pin clears the window; the ledger's ordinary scope is direct dependencies, and this is the one place a transitive version is a decision rather than a resolution, so it is the one place a transitive pin owes a row of its own. All versions are pinned exactly (no ranges); lockfiles are committed and CI restores in locked mode so drift fails the build; internal packages resolve only from the internal feed. Container images are dependencies too: every image reference is pinned tag-plus-digest, one value across every surface that names it, and ledgered like a package (INV-05). Every project carries a ledger recording versions, publish dates, and waivers. A vendored component's own internal window governs that component's development, never what the host project consumes. The kernel a project is seeded from is itself a dependency: its identity (remote URL, commit, catalog pass date, edition) is ledgered in the project's VERSIONS.md (the kernel-provenance section), written mechanically at instantiation, and changed only by a deliberate upgrade that lands the new pin in the same change as the re-copied mechanisms.

**Harm.** Supply-chain compromise is loudest in a package's first days; the window buys the ecosystem time to catch it. Range pins and unlocked restores mean the build you tested is not the build you shipped. Dependency confusion substitutes a public package for an internal name. An unpinned kernel seed is lost provenance: the project's conformance statement ("conformant to the catalog as of the pin") becomes unverifiable, its drift from the kernel uncomputable, and the loss is unrecoverable after the fact.

**Enforcement.**
- Mechanism class: exact pins + committed lockfiles + locked-mode restore in the CI loop + source mapping + the ledger file + the docs-lint image check (a floating or unledgered container-image reference fails the build); a CI publish-date check against the window is the named upgrade path (decided at kernel build whether it makes v1; the ledger, pins, and locked restore are unconditionally v1).

**Weakening notes.** The window's value is the catalog's own ruling and is deliberately independent of any standing policy outside this repository, in either direction. It has been re-derived from an external policy once, when an invariants pass raised it on the grounds that the extracted number contradicted a policy the catalog cannot see, and it has since been re-ruled on evidence from a build. The independence is recorded because without it the next pass reads that reasoning, finds the external policy unchanged, and flips the number back for a reason that is not evidence. An external policy is an input to a catalog ruling and never a reason on its own; changing the number is a dated pass carrying its evidence, which is also what makes every project's pin to a catalog version meaningful.

A prior ledger omitted several shipped packages (pinned but unledgered), showing the ledger needs its own check: the kernel's ledger lint compares ledger rows against the lockfile's direct dependencies. Vendored assets record their hash in the ledger (a vendored-asset sha256 idiom, promoted from Bucket 4). The kernel pin proves identity, not conformance: the loop (TEST-3) holds a project's mechanisms true, and the check verifies the row is filled, not that the named commit is real; the commit is corroborated at upgrade time, when the kernel-owned paths are re-copied against it.
